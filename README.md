## 1. Общие сведения

### 1.1. Наименование программного комплекса

Полное наименование разрабатываемого продукта — комплекс программных средств «Task Manager». Краткое наименование — Task Manager.

### 1.2. Краткая характеристика продукта

**Task Manager** — кроссплатформенное приложение, предназначенное для управления задачами и проектами. Оно позволяет пользователям создавать задачи, назначать исполнителей, задавать сроки выполнения, отслеживать текущие статусы и фиксировать результаты работы. Приложение ориентировано на использование как на мобильных устройствах, так и на компьютерах.

Проект реализуется с использованием Flutter, что позволяет применять единую кодовую базу для Android и Windows. При этом интерфейс и основные пользовательские сценарии должны учитывать особенности каждой целевой платформы.

### 1.3. Область применения

Приложение может использоваться для личного планирования, командной работы и координации проектной деятельности. Оно должно обеспечивать единое представление задач и проектов, помогать пользователям контролировать сроки и приоритеты, а также сохранять возможность работы с данными при временном отсутствии подключения к интернету.

### 1.4. Основание для разработки

Разработка приложения инициирована на основе следующих факторов. Они отражают предполагаемые потребности пользователей и организационные задачи, которые должен решать продукт:

- **Анализ рынка**: Растущий спрос на инструменты удалённой работы и управления проектами (рынок вырос на 30% за 2023–2024 гг.). Пользователи ожидают доступа к задачам с любых устройств.
- **Бизнес-задача**: Создание конкурентного решения, сочетающего простоту использования с расширенными функциями, доступными в дорогих Enterprise-системах.
- **Техническая необходимость**: Отсутствие современного кроссплатформенного решения для среднего бизнеса с возможностью полной офлайн-работы и нативной производительностью.
- **Внутренние потребности**: Автоматизация рутинных процессов планирования и повышение прозрачности выполнения задач внутри компании с возможностью работы в полях (без интернета).

### 1.5. Общая характеристика решения

Программный комплекс предназначен для работы на мобильных устройствах и персональных компьютерах. Клиентская часть планируется к реализации на Flutter с использованием единой кодовой базы для Android и Windows. Серверная часть обеспечивает хранение и обработку данных, взаимодействие через API и поддержку синхронизации.

## 2. Назначение комплекса программных средств «Task Manager»

### 2.1. Основное назначение

Комплекс программных средств «Task Manager» предназначен для планирования, распределения и контроля выполнения задач и проектов. Он обеспечивает централизованное представление рабочих задач, помогает отслеживать сроки и приоритеты, а также поддерживает доступ к данным с разных устройств.

### 2.2. Целевая аудитория

1.  **Физические лица (Freelancers)**: Для личной организации и планирования задач на всех устройствах.
2.  **Менеджеры проектов**: Для контроля сроков, ресурсов и распределения нагрузки вне офиса.
3.  **Мобильные сотрудники**: Курьеры, инженеры, полевые работники, которым нужен офлайн-доступ к задачам.

### 2.3. Цели использования комплекса

- **Повышение продуктивности**: Сокращение времени на планирование и согласование задач на 20% за счёт доступности с любого устройства.
- **Автоматизация**: Автоматическое уведомление о дедлайнах и изменение статусов при выполнении.
- **Аналитика**: Сбор данных для построения отчётов по эффективности команд и отдельных сотрудников.
- **Офлайн-доступ**: Возможность работать с задачами без подключения к интернету с последующей синхронизацией.

## 3. Описание услуги «Task Manager»

### 3.1. Общие сведения об услуге

Услуга заключается в предоставлении пользователю программных средств для ведения задач и проектов, координации участников и контроля текущего состояния работ. Пользователь может создавать задачи, назначать исполнителей и сроки, изменять статусы и получать уведомления о важных событиях. При отсутствии интернет-соединения предусмотрена работа с локально сохраненными данными с последующей синхронизацией.

### 3.2. Основные пользовательские возможности

Приложение предусматривает следующие основные возможности:
- создание задач с описанием, сроками выполнения и приоритетами;
- назначение исполнителей и контроль статусов выполнения;
- объединение задач в проекты и категории;
- поиск и фильтрацию задач по заданным параметрам;
- получение уведомлений о приближающихся сроках и изменениях;
- работу в офлайн-режиме с последующей синхронизацией данных;
- просмотр статистики для анализа продуктивности.

Перечисленные возможности определяют общий функциональный контур продукта и раскрываются в требованиях к программному обеспечению ниже.

### 3.3. Сценарии использования

1. Пользователь входит в приложение или проходит регистрацию.
2. Создает проект либо открывает существующий и добавляет задачи.
3. Указывает описание, приоритет, срок выполнения и исполнителя, при необходимости добавляет комментарии и вложения.
4. Отслеживает ход выполнения через статусы, доску задач, поиск и фильтры.
5. Получает уведомления о приближающихся сроках и изменениях.
6. При работе без сети изменения сохраняются локально; после восстановления соединения приложение передает их на сервер и выполняет синхронизацию.
7. Руководители и администраторы используют административную панель для управления учетными записями, ролями и отчетностью.

### 3.4. Результат предоставления услуги

Результатом использования комплекса является единое рабочее пространство для учета задач и проектов, повышение прозрачности выполнения работ, упрощение контроля сроков и доступность актуальных данных на поддерживаемых устройствах. Целевые показатели эффективности приведены в разделе 4 настоящего документа.

## 4. Требования к системе

### 4.1. Функциональные требования

Система должна предоставлять перечисленные ниже функции. Реализация функций должна учитывать согласованность данных между клиентскими устройствами и серверной частью.

Функциональные требования определяют операции, доступные пользователям и администраторам системы. Перечисленные ниже возможности сгруппированы по назначению, чтобы упростить проектирование отдельных модулей и последующую проверку их работы.

- **Модуль аутентификации**:
  - Регистрация/Вход по email/паролю или через Google.
  - Биометрическая аутентификация (Fingerprint / Face Unlock) на Android и Windows Hello на Windows.
  - Двухфакторная аутентификация (2FA) для корпоративных аккаунтов.
  - Восстановление пароля по email.
- **Управление задачами**:
  - CRUD-операции (Создание, Чтение, Обновление, Удаление) для задач.
  - Установка приоритета (Low, Medium, High, Critical).
  - Назначение дедлайна и исполнителей.
  - Комментарии и вложения (фото, файлы, голосовые заметки) к задачам.
  - Связь между задачами (блокировка, зависимость).
- **Управление проектами**:
  - Создание проектов и объединение в них задач.
  - Назначение руководителя проекта и участников.
  - Ведение доски с колонками (To Do, In Progress, Done) или Kanban-доски с drag-and-drop.
- **Поиск и фильтрация**:
  - По названию, описанию, тегам, статусу, приоритету, исполнителю.
  - Сохранение пользовательских фильтров.
- **Уведомления**:
  - Push-уведомления на Android (FCM) и Windows (WNS / Firebase Cloud Messaging).
  - Локальные уведомления (`flutter_local_notifications`) для автономных таймеров и напоминаний.
  - Напоминания о приближающихся дедлайнах.
- **Личный кабинет**:
  - Просмотр всех своих задач (мои задачи, задачи в работе, завершённые).
  - Настройка личного профиля и предпочтений уведомлений.
- **Офлайн-режим (Offline-First)**:
  - Локальное хранение данных в реляционной БД (SQLite) с шифрованием.
  - Автоматическая синхронизация с сервером при восстановлении соединения и алгоритмы разрешения конфликтов.
- **Административная панель (веб-интерфейс)**:
  - Управление пользователями и их ролями (Admin, Project Manager, User).
  - Просмотр логов действий для аудита.
  - Генерация отчётов по продуктивности команды.

### 4.2. Нефункциональные требования

Нефункциональные требования описывают ожидаемые характеристики качества приложения: производительность, доступность, безопасность, масштабируемость и совместимость с целевыми платформами. Эти характеристики должны учитываться при проектировании архитектуры и проведении испытаний.

- **Производительность**: Приложение должно работать плавно на всех целевых устройствах, включая устройства с 2 ГБ ОЗУ. Время отклика пользовательского интерфейса — менее 100 мс.
- **Доступность**: Серверная часть — 99.9% (не более 8 часов простоя в год). Приложение должно быть доступно в офлайн-режиме.
- **Безопасность**:
  - Хранение паролей с использованием bcrypt на сервере.
  - Хранение данных на клиенте с шифрованием (SQLCipher).
  - HTTPS с валидными SSL-сертификатами.
  - Защита от основных угроз OWASP Top 10.
  - Разграничение прав доступа (Role-Based Access Control).
- **Масштабируемость**: Модульная монолитная архитектура с возможностью горизонтального масштабирования stateless-сервисов и репликации базы данных.
- **Кроссплатформенность**:
  - **Android**: Android 8.0+ (API 26+).
  - **Windows**: Windows 10/11 64-bit (x64 / ARM64).
- **Офлайн-возможности**: Приложение должно поддерживать полную работу без интернета с локальным кешированием в SQLite и очередью отложенных изменений.

### 4.3. Технический стек

Ниже приведён планируемый набор технологий для серверной, клиентской и административной частей. Выбор конкретных вариантов, обозначенных через косую черту, должен быть согласован в ходе проектирования с учётом требований проекта и совместимости компонентов.

#### Backend (Серверная часть)
- **Язык**: Python 3.10+.
- **Фреймворк**: FastAPI (модульный монолит).
- **База данных**: PostgreSQL (основная), Redis (кеширование, сессии, брокер задач).
- **Очереди**: Celery для асинхронной обработки (уведомления, отчёты).
- **Сервер**: Gunicorn + Nginx.
- **API**: RESTful API с автогенерацией OpenAPI-спецификации.

#### Frontend (Клиентская часть — Кроссплатформенная)
- **Фреймворк**: Flutter (Dart) — единая кодовая база для Android и Windows.
- **Навигация**: GoRouter / AutoRoute.
- **Стейт-менеджмент**: Riverpod / BLoC.
- **Хранение**: SQLite + Drift + SQLCipher (шифрованное реляционное хранилище).
- **Push-уведомления**: Firebase Cloud Messaging (Android/Windows) + `flutter_local_notifications` (для локальных напоминаний).
- **Сборка**: Нативные билды под Android (APK/AAB) и Windows (EXE/MSIX).

#### Административная панель (веб)

- **Фреймворк**: React / Vue.js для менеджеров и администраторов; возможность реализации на Flutter также рассматривается.

### 4.4. Требования к окружению разработки

Для подготовки рабочего окружения необходимо установить инструменты для контроля версий, запуска инфраструктуры, сборки клиентских приложений и разработки серверной части. Состав окружения должен обеспечивать возможность локального запуска, проверки и отладки основных компонентов системы.

- Установленный Git.
- Docker и Docker Compose (для локального запуска инфраструктуры).
- **Для Flutter**: Flutter SDK, Android Studio (для Android), Visual Studio 2022 с C++ workload (для Windows).
- **Для Backend**:
  - Python 3.10+, PostgreSQL и Redis.
- Переменные окружения (`.env` файл) для подключения к БД, Redis и внешним API.
- Makefile или скрипты для автоматизации команд сборки.

### 4.5. Требования к документации

Документация входит в состав результатов разработки и должна обеспечивать возможность установки, эксплуатации, сопровождения и дальнейшего развития системы.

Документация по проекту является неотъемлемой частью поставки и должна обеспечивать полное понимание системы для всех категорий участников: разработчиков, тестировщиков, администраторов и конечных пользователей. Документы должны поддерживаться в актуальном состоянии и соответствовать реализованной версии программного обеспечения.

### 4.5.1. Состав документации

В состав документации входят материалы, необходимые для описания требований, архитектуры, интерфейсов, данных, установки и эксплуатации системы. Каждый документ должен решать свою задачу и дополнять остальные материалы, не дублируя без необходимости их содержание.

- **Техническое задание (ТЗ)** – утверждённый документ с требованиями заказчика.
- **Архитектурная документация** – описание компонентов системы, схемы данных, взаимодействия сервисов, диаграммы последовательности (C4-модель).
- **API-документация** – спецификация всех REST-эндпоинтов в формате OpenAPI (Swagger) с примерами запросов/ответов.
- **Документация по базам данных** – ER-диаграмма, описание таблиц, индексов, миграций.
- **Руководство разработчика** — инструкции по установке зависимостей, сборке проекта, запуску тестов и линтеров, а также описание структуры исходного кода и основных правил разработки.
- **Руководство администратора** – описание развертывания в production, настройка мониторинга, резервное копирование, восстановление, обновление.
- **Руководство пользователя** – описание интерфейса, сценариев использования, решения типовых проблем для Android и Windows.
- **Тест-план и тест-кейсы** – документы для QA-команд.

### 4.5.2. Форматы и хранение

Документация хранится совместно с исходным кодом, чтобы изменения требований и реализации можно было отслеживать в системе контроля версий. Структура каталогов и правила именования файлов должны быть единообразными; диаграммы и спецификации должны быть доступны участникам проекта в удобном для просмотра виде.

- Все текстовые документы хранятся в репозитории в формате Markdown (`.md`) для удобства версионирования.
- Схемы и диаграммы сохраняются в виде файлов `drawio` или `puml`, а их экспортированные версии (PNG/SVG) помещаются в папку `/docs/images`.
- API-документация генерируется автоматически из кода и доступна по эндпоинту `/api/docs` (Swagger UI) и `/api/redoc`.
- Версии документации синхронизируются с релизными тегами (каждому релизу соответствует своя версия docs).

### 4.6.1. Технические показатели (на production-контуре)

Показатели ниже рассматриваются как целевые значения для production-контура. Их достижение проверяется предусмотренными методами измерения, мониторинга и нагрузочного тестирования.

| Показатель | Плановое значение | Методика измерения |
| :--- | :--- | :--- |

## 5. Состав и содержание работ по доработке программных средств

Работы по доработке выполняются последовательно: от анализа и проектирования до разработки функциональных модулей, интеграции, тестирования и выпуска релиза. Работы организуются по Scrum с двухнедельными спринтами. Конкретный состав задач уточняется в рамках планирования этапов, при этом требования настоящего документа служат основой для проверки результата.

### 5.1. Состав работ

Проектирование локального хранилища и офлайн-архитектуры предусмотрено на первых этапах, поскольку эти решения влияют на структуру данных и порядок синхронизации между клиентом и сервером. Состав этапов и их результаты представлены в таблице.

## 6. Состав и содержание работ по развертыванию

Развертывание включает подготовку окружения, настройку серверных компонентов и баз данных, сборку клиентских приложений, проверку конфигурации и публикацию согласованной версии. Развертывание должно выполняться по воспроизводимой инструкции, с учетом резервного копирования и возможности восстановления после сбоя.

### 6.1. Подготовка окружения

Для разработки и подготовки релиза предусматриваются следующие инструменты и компоненты:

- Git для контроля версий исходного кода;
- Docker и Docker Compose для локального запуска инфраструктуры;
- Flutter SDK, Android Studio для Android-сборки и Visual Studio 2022 с C++ workload для Windows-сборки;
- Python 3.10+, PostgreSQL и Redis для серверной части;
- файл переменных окружения `.env` для параметров подключения к базе данных, Redis и внешним API;
- Makefile или скрипты для автоматизации команд сборки и запуска.

### 6.2. Развертывание компонентов

1. Подготовить целевое окружение и проверить доступность требуемых сервисов.
2. Настроить серверную часть на базе Python и FastAPI, подключить PostgreSQL и Redis, настроить запуск через Gunicorn и Nginx.
3. Настроить параметры доступа и защищенное соединение HTTPS с действительными SSL-сертификатами.
4. Собрать клиентские приложения для Android в форматах APK/AAB и для Windows в формате EXE/MSIX.
5. Настроить доступ к API, уведомлениям и синхронизации данных.
6. Выполнить проверку работоспособности в тестовом окружении и smoke-тестирование перед публикацией.
7. Подготовить резервную копию и проверить процедуру восстановления либо отката.
8. Выполнить публикацию согласованной версии и передать сопровождающую документацию.

### 6.3. Публикация и передача в эксплуатацию

В плане релиза предусмотрена публикация Android-приложения в Google Play, Windows-сборки через согласованный канал распространения, а серверной части — на подготовленном веб-сервере. До фактического выпуска необходимо проверить готовность компонентов, актуальность документации и выполнение критериев приемки. Перенос данных выполняется только при необходимости и в рамках согласованной процедуры.

## 7. Порядок контроля и приемки

Контроль качества проводится на протяжении всего жизненного цикла разработки. Приемка выполняется на основании результатов тестирования, соответствия реализованных функций требованиям настоящего документа и устранения критических замечаний.

### 7.1. Организация контроля качества

Контроль качества должен выявлять дефекты на ранних этапах и подтверждать, что изменения не нарушают уже реализованные функции. Для этого используются проверка кода, статический анализ, модульные и интеграционные тесты, а также испытания на физических устройствах.
- **Code Review** – каждый Pull Request проверяется минимум двумя разработчиками (используется GitHub Pull Requests с обязательными аппрувами).
- **Статический анализ** – автоматический запуск линтеров (Pylint, Flutter Analyze) и проверка форматирования через pre-commit хуки.
- **Модульное и интеграционное тестирование**:
  - Backend: покрытие тестами (PyTest) ≥ 80%.
  - Frontend: покрытие бизнес-логики и стейт-менеджмента (BLoC/Riverpod) ≥ 70%, UI-виджетов — по ключевым пользовательским сценариям.
- **Интеграционное тестирование** – проверка взаимодействия компонентов и внешних систем (email-шлюзы, push-сервисы) в отдельной среде staging.
- **Тестирование на реальных устройствах** – проверка на физических Android-устройствах и Windows-ПК (x64/ARM64).

### 7.2. Критерии приемки релиза

Релиз может быть передан на приёмку после проверки выполнения основных требований и подтверждения работоспособности приложения в предусмотренных режимах. Критерии приёмки включают следующие условия:
- Все автоматические тесты (CI/CD пайплайн) проходят успешно.
- Критические и высокоприоритетные баги (Severity ≥ Major) исправлены или задокументированы с планом исправления.
- Приложение успешно запускается и работает на Android и Windows в онлайн и офлайн режимах.
- Документация обновлена и соответствует текущей версии кода.
- Получено согласование от владельца продукта (Product Owner) по результатам демонстрации.
- Проведено smoke-тестирование на production-подобном окружении.
- Выполнено бэкап-восстановление (проверка процедуры отката).

### 7.3. Процедура приемочного тестирования (UAT)

Приёмочное тестирование проводится по заранее подготовленному набору тест-кейсов. Его задача — подтвердить, что реализованные пользовательские сценарии соответствуют ожиданиям заказчика и приложение пригодно к использованию на поддерживаемых платформах.

1. Заказчик (или представитель) выполняет предопределённый набор тест-кейсов на Android и Windows.
2. Все расхождения фиксируются в баг-трекере (Jira).
3. После устранения критических замечаний заказчик подписывает акт приёмки выполненных работ.
4. Версия получает тег `release-x.y.z` в репозитории, и начинается развертывание на production.

## 8. Гарантийная поддержка

Гарантийная поддержка предназначена для регистрации, анализа и устранения дефектов, выявленных после передачи программного комплекса. Точный гарантийный срок и порядок взаимодействия сторон в исходном README не установлены; эти условия должны быть согласованы отдельно и зафиксированы в окончательной версии технического задания.

### 8.1. Регистрация и классификация обращений

Для учета дефектов используется баг-трекер с классификацией по приоритетам: Blocker, Critical, Major, Minor и Trivial. Каждое обращение должно содержать описание проблемы, шаги воспроизведения, ожидаемый и фактический результат, сведения об устройстве и версии приложения, а также материалы, помогающие воспроизвести ошибку, если они доступны.

### 8.2. Время реакции на дефекты

В исходных требованиях предусмотрены следующие целевые сроки реакции:

- **Blocker** — в течение 4 часов;
- **Critical** — в течение 24 часов;
- **Major** — в течение 3 рабочих дней.

Сроки устранения дефектов, порядок обработки обращений с приоритетом Minor и Trivial, часы доступности поддержки и каналы связи необходимо согласовать дополнительно. Время реакции означает начало обработки обращения и само по себе не является сроком полного устранения проблемы.

### 8.3. Сопровождение и развитие

В рамках сопровождения предусматриваются поддержание стабильности программного комплекса, выпуск обновлений, исправление подтвержденных дефектов и развитие функциональности. Перед выпуском обновлений должны выполняться необходимые проверки, а документация должна актуализироваться в соответствии с изменениями системы.
